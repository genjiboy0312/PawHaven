# 서버 재화·상점·보상 (2026-10-17)

## 범위와 연동
- Google 로그인 실사용 테스트는 사용자 요청으로 보류. 기존 이메일 로그인은 유지한다.
- 게스트는 기존 ShopState 로컬 프로토타입을 사용한다. 로그인한 계정은 ServerShopState/EconomyClient로 서버 결과만 적용한다.
- 최초 서버 지갑은 1,000코인과 Hat/Body/Acc/Etc 1번 기본 아이템을 제공한다. 기기 테스트 코인·소유 아이템·보상 내역을 서버에 올리지 않는다.
- 강아지·의상·프리셋·Home은 기존 꾸미기 클라우드를 유지한다. 서버 소유권이 확인되면 현재 착용을 점검하고, Character 목록은 서버가 인정한 소유 아이템을 반영한다.
- 새 migration: supabase/migrations/202610170002_server_economy.sql. 기존 프로필/꾸미기 테이블을 삭제하거나 변경하지 않는다.
- Supabase SQL Editor에서 새 파일 전체를 실행해야 한다. 공개 키로는 SQL을 적용할 수 없다.

## 서버 규칙
- 클라이언트는 액션/요청 UUID/아이템 번호 등만 보낸다. auth.uid()에서 계정을 결정하고 가격·잔액·지급액·레벨·소유권은 서버가 계산한다.
- 가격은 기존과 동일하게 75 + floor((index-1)/5) × 25. 중복 구매는 재차 차감하지 않고 잔액 부족 시 아이템을 주지 않는다.
- 지갑 행을 FOR UPDATE로 잠근 한 트랜잭션에서 잔액·소유권·보상 기록·재시도 기록을 함께 처리한다.
- 동일 요청 UUID와 동일 payload는 한 번만 실행한다. 응답 유실 후 재시도에는 현재 최신 지갑과 원래 실행 결과를 반환한다. 같은 UUID에 다른 명령/payload를 붙이면 거부한다.
- 일일 초기화는 서버 Asia/Seoul 날짜 기준이다. 게스트의 기존 기기 시간 기준은 유지한다.
- 교감은 서버 시간 10초 간격·하루 3회까지만 집계. 3회 완료 보상 50코인.
- Play 시작은 서버에서 15분 유효·계정 귀속 토큰을 발급받는다. 새 Play를 시작하면 이전 미완료 토큰은 폐기한다.
- 완주는 토큰 발급 후 최소 4초, 유효 기간 내, 본인 미사용 토큰일 때만 1회 인정한다. 100 XP(최대 400), 일일 완주 1회 조건. 일일 완주 보상 100코인.
- 패스는 레벨/프리미엄 자격/중복 수령을 검증한다. 1~5단계 무료 보상 20×단계, 프리미엄 보상 40×단계.
- 시즌 0 무료 테스트 해금은 기존처럼 유지한다. 이 엔드포인트는 실제 유료 패스가 아니다. 실제 판매 전에 별도 결제 검증과 유료 자격 지급으로 교체해야 한다.
- 유저별 변경 명령은 분당 120개 제한. 재시도 기록을 다시 읽는 요청은 추가 차감/변경을 하지 않는다.

## 권한과 실패 처리
- 지갑/아이템/보상 테이블은 RLS로 본인 SELECT만 허용하고 일반 클라이언트의 직접 쓰기는 전부 금지한다.
- 요청 기록/플레이 토큰은 일반 사용자의 직접 읽기/쓰기를 모두 금지한다.
- 경제 RPC는 인증 사용자만 실행 가능. SECURITY DEFINER는 직접 쓰기가 금지된 서버 트랜잭션을 수행하기 위해 쓰며, 빈 search_path와 명시적 스키마, auth.uid() 검사를 사용한다. 내부 snapshot helper는 비공개 스키마에 두고 외부 실행 권한을 주지 않는다.
- EconomyClient는 메모리 내 순서 있는 요청 큐를 사용한다. 응답 유실 시 같은 UUID를 재시도하고, 앞선 요청 때문에 대기한 완주 기록도 다음 재시도에 처리한다.
- 서버 확인 전 코인 차감·아이템 지급·보상 수령을 낙관적으로 반영하지 않는다. 처리 중 구매/보상 버튼은 잠그고 실패 시 로비·상점·퀘스트에 재시도를 표시한다.
- 로그아웃/계정 교체 시 이전 큐를 종료하고 늦은 응답을 새 계정에 적용하지 않는다.
- 큐는 브라우저 새로고침까지 보관하지 않는다. 새로고침 후 서버를 다시 읽으면 이미 확정된 구매/보상은 복원된다. 확정되지 않은 활동 기록은 오프라인 보상으로 재생하지 않는다.
- 서버 정보는 최대 30초 간격으로 다시 확인한다. 클라이언트 시각을 바꿔 계정 일일 진행도를 초기화할 수 없다.
- Play 시작 응답을 기다리는 동안 다른 씬으로 이동했다면 나중에 도착한 응답이 게임씬을 덮어쓰지 않는다.

## 검증과 한계
- 전체 자동 테스트 101개·타입 검사·프로덕션 빌드를 검증한다.
- 추가 19개 테스트는 PGlite의 실제 PostgreSQL/PLpgSQL에서 migration을 적용해 구매 금액, 중복 재시도, 지급 조건, 날짜 초기화, 토큰, 권한을 실행한다.
- 실제 DB 결과와 JS 어댑터를 연결해 응답 유실·후속 완주 큐·계정 종료·잘못된 응답·조회 간격·기존 게스트 보존·구매 버튼 잠금·Character 소유권 갱신을 확인한다.
- 테스트 계정 UUID/가짜 auth 스키마는 로컬 테스트 DB 안에서만 만든다. 운영 Supabase 사용자/메일을 자동 생성하거나 발송하지 않는다.
- Supabase 실제 로그인/두 사용자 RLS/Google OAuth/PC↔모바일 동기화는 아직 실계정 확인 전이다.
- 토큰과 시간 검사는 기초 검증이다. 게임 플레이 자체는 클라이언트에서 실행하므로 서버가 이동/충돌/점프 과정을 재현해 완주를 증명하는 부정행위 방지까지 완성한 것은 아니다.
- 실제 결제·광고 보상·운영 시즌 종료·장기 요청 기록 정리는 별도 단계다.

- 재화 요청은 요청 시점에 확인한 계정의 JWT를 명시적으로 고정해 보낸다. 공유 SDK 세션이 다른 로그인으로 바뀌어도 이전 요청이 새 계정 지갑을 변경하지 않는다. 계정 불일치/취소 시 전송 전에 중단한다.

## 실제 Supabase 적용 확인
- 사용자가 두 번째 재화 migration 실행 완료를 확인했다.
- 실제 프로젝트 API에서 economy_wallets/items/claims/requests/runs 5개 테이블의 비로그인 SELECT가 모두 42501로 거부됨을 확인했다.
- economy_command도 함수 미존재(PGRST202) 대신 실행 권한 없음(42501)을 반환해 생성과 비로그인 차단을 확인했다.
- 실제 사용자 JWT로 구매/보상·두 계정 RLS·기기 간 복원 검증은 Google 로그인 연동 때 진행한다.
