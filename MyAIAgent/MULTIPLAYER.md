# 모드 선택·멀티 레이스 프로토타입 (2026-10-19)

## 사용자 승인 범위
- Play → Single/Multiplayer. Single은 맵 선택 후 기존 코스 플레이.
- 방 목록은 한 페이지 2행×2열/4개, 가로 스와이프·스크롤 스냅·이전/다음·페이지 번호. 방 이름/맵/대기·진행 상태/인원 ? / 4 표시.
- 최대 4인 공개 방 생성·입장. 방장만 맵 선택, 방원 Ready/취소, 최소 2인+방원 전원 Ready 때 시작.
- 맵 변경 시 Ready 초기화. 진행 중 입장 금지. 방장 퇴장 시 먼저 입장한 생존 멤버로 이전.
- 3초 서버 시각 카운트다운, 서로 통과하는 레이스, 서버 순위, 결과 확인 후 같은 대기방 복귀.

## 서버 적용
1. 기존 계정/재화 migration이 적용된 Supabase SQL Editor에서 `supabase/migrations/202610190003_multiplayer.sql` 최종본 전체 실행.
2. 새 RPC를 확인하고 실제 서로 다른 Google 계정/기기로 방 생성→입장→Ready→Start→완주→복귀를 확인한다.
3. 적용 전 UI는 서버 준비 안내를 표시한다. 로컬 방/가짜 플레이어를 운영 화면에 만들어 실제 멀티처럼 보여주지 않는다.

새 테이블은 mp_rooms / mp_members / mp_racers. RLS 활성화, anon/authenticated의 직접 테이블 권한 없음. authenticated만 multiplayer_command를 실행하며 모든 명령은 auth.uid()로 실행자를 결정한다. 방 정보 조회도 로그인이 필요하다. 닉네임과 동물/착용 정보는 서버 프로필/저장/보유권에서 구성하며 이메일은 방에 노출하지 않는다.

서버에서 마지막 자리·한 계정의 한 방 가입·방장 권한·Ready·3초 출발·라운드 ID·완주 기록을 검증한다. 퇴장/45초 이상 heartbeat 없는 멤버를 정리하고 방장을 이전한다. 카운트다운 중 2명 미만이면 취소한다. 첫 완주 후 20초 또는 라운드 최대 120초가 지나면 결과로 전환한다. 전원 완주 시 다음 동기화에서 바로 결과로 이동한다. 결과를 확인한 사람은 대기방에서 기다리고, 모두 돌아오면 다음 Ready를 받을 수 있다.

## 재사용·연결
- PlayMenuPopup은 Settings의 모달·포커스/입력 차단·버튼 스타일과 기존 정원 이미지를 재사용한다.
- 맵은 CourseCatalog의 정원 산책길(20~30초)과 기존 연습 마당(8~12초). 새 아트/라이브러리를 추가하지 않는다.
- 싱글은 기존 경제 run_start/run_finish/퀘스트 흐름을 유지한다. 멀티 결과는 별도 서버 라운드이며 이번 버전에서 코인/XP/일일 완주 보상을 새로 지급하지 않는다.
- 멀티는 현재 서버 저장의 동물과 착용을 기준으로 표시한다. 입장/생성 전 보류된 꾸미기 저장을 시도한다. 다른 참가자는 기존 AnimalAnimationController/AnimalEffects와 이름 표시를 사용한다.
- RoomClient는 로그인 소유자의 토큰을 요청마다 고정하며 계정 전환/종료 뒤 이전 응답을 적용하지 않는다. 종료 시 방 퇴장을 시도하고 네트워크 실패는 heartbeat 만료로 정리한다.

## 동기화와 한계
- 별도 WebSocket 서버나 Realtime publication 설정 없이 RPC를 재사용한다. 대기/방 목록은 요청 완료 후 약 1.2초, 레이스/카운트다운은 약 0.3초 뒤 다음 요청을 보낸다. 동시에 요청을 겹쳐 보내지 않는다.
- 동작/위치는 저빈도 스냅샷과 화면 보간·짧은 수평 예측으로 표시한다. 서버는 인증된 본인 포즈만 갱신하고 좌표 범위를 제한하지만 물리/입력 자체는 클라이언트에서 계산한다.
- 멀티 기록은 서버 출발/접수 시각으로 정하며 최소 시간·피니시 위치·라운드를 확인한다. 이는 완전한 부정행위 방지가 아니다. 멀티 기록을 유료 재화/경쟁 보상 기준으로 쓰기 전에 서버 권위 시뮬레이션과 추가 검증이 필요하다.
- 전역 advisory lock을 사용하는 소규모 프로토타입이다. 활성 방/사용자 증가 전에는 방별 동시성 설계와 전용 실시간 전송을 검토해야 한다. 방 목록은 최근 80개를 표시한다.
- 창을 닫으면 즉시 종료를 보장하지 않고 45초 TTL로 정리한다. 앱 전환/느린 네트워크는 결과와 조작에 지연을 줄 수 있다. 게임 Settings는 해당 기기 입력만 멈추며 서버 레이스 시계와 다른 참가자는 계속 진행한다.
- 초기 서버 SQL 적용과 실기기 2~4인/네트워크 지연·재접속 검증은 자동 테스트와 구분한다.

## 2026-10-20 대기방 UI
- 사용자가 SQL 실행 완료를 알렸으며, 운영 RPC의 익명 호출에서 42501(권한 거부)을 확인했다. 함수 등록과 비로그인 차단 확인이며, 실제 두 계정 동시 플레이 검증과는 구분한다.
- 기존 Settings/commerce 표면과 맵 이미지를 재사용한다. 서버 참가자의 선택 동물 Idle 시트를 CSS 배경으로 잘라 표시하며 새 이미지·라이브러리·렌더러를 추가하지 않는다. 착용 아이템을 합성한 미리보기는 이번 범위에서 제외한다.
- 4개 슬롯에 닉네임/방장 왕관/Ready 체크를 표시한다. 방장과 준비 완료 슬롯은 연두색, 빈 슬롯은 옅은 점선으로 구분한다.
- 선택 맵 미리보기는 모두에게 보이고 변경 버튼은 방장만 보인다. 인원 부족/준비 대기/방장 시작 대기/시작 가능 안내를 서버 스냅샷에서 계산한다. 기존 서버의 시작 권한과 Ready 조건은 유지한다.
- 입장·퇴장·방장 변경은 6초 상태 메시지로 표시하며 방장 변경을 우선한다. 네트워크 실패는 기존 연결 안내/재시도를 사용한다.
- Idle 갱신 타이머는 모달 재표시/닫기/계정 전환 시 해제한다. 백그라운드에서는 갱신을 건너뛰고 reduced-motion에서는 첫 프레임으로 표시한다.
- 전체 126개 테스트 통과: 실제 SQL 기반 Ready 표시/게스트 시작 권한/방장 이전 안내/애니메이션 타이머 해제 포함. 타입 검사·프로덕션 빌드 통과. 추가 SQL 실행은 필요 없다. 실제 모바일 배치와 서로 다른 계정의 동시 플레이는 별도 확인 대상이다.

## 2026-10-20 멀티 결과 화면
- RaceResults 공용 DOM 목록을 플레이 결과와 대기방 결과에서 재사용한다. 기존 Idle 아틀라스 크롭은 PetPortrait로 공유하며 새 이미지·라이브러리·SQL은 추가하지 않는다.
- 서버가 인정한 time 기준으로 정렬하고 완주자에게만 순위를 표시한다. 같은 기록은 같은 순위, 기록 없는 참가자는 순위 대신 대시를 표시한다. 진행 중에는 '달리는 중', 종료 또는 퇴장 후에는 '미완주'를 표시한다.
- 강아지 정지 미리보기/닉네임/초 단위 기록을 표시하고 본인 행은 연두색과 '나/You' 문구로 구분한다. 플레이 씬은 라운드 참가자 모습을 보관하여 도중 퇴장한 참가자도 확인 가능하다. 대기방 결과는 현재 서버 멤버 정보가 없는 참가자의 그림을 임의로 대체하지 않는다.
- 먼저 완주하면 서버 endsAt 기준 남은 초를 표시한다. 0초에서도 클라이언트가 종료·순위를 확정하지 않고 다음 서버 결과를 기다린다. 연결 오류는 남은 시간 대신 연결 안내로 표시한다.
- 서버 결과 수신 후 따뜻한 한 줄과 대기방 복귀 버튼을 표시한다. 기존 페이드/같은 방 복귀/다음 Ready 흐름을 유지하며 코인·XP 보상은 추가하지 않는다.
- 멀티 결과 패널은 중앙 크림색 패널과 참가자 슬롯 스타일을 재사용하고 결과 표시 중 조작 UI는 숨긴다. 싱글 결과 화면은 유지한다.
- 전체 127개 테스트·타입 검사·프로덕션 빌드 통과. 검증에는 서버 기반 대기 타이머/순위·미완주 구분/본인 강조/기존 결과 후 복귀가 포함된다. 실계정 2인 및 모바일 시각 검증은 별도 확인 대상이다.

## 2026-10-20 연결 복구
- 네트워크 오류/online·offline/창 포커스/visibilitychange 뒤에는 sync 또는 list로 서버 상태를 먼저 읽는다. 확인 중 Ready/Start/맵 변경/입장/완주 재전송과 레이스 조작을 막고 기존 상태 안내 영역에 재연결 문구를 표시한다.
- 요청은 12초 timeout과 소유자 종료 AbortSignal을 결합한다. 백그라운드에서는 새 폴링을 멈추고, 복구 세대가 바뀌기 전 요청의 늦은 응답은 적용하지 않는다. 종료 시 브라우저 이벤트·타이머를 해제한다.
- 응답만 잃은 Ready/Start는 자동 재실행하지 않는다. 완주는 먼저 서버 기록을 확인하고, 같은 라운드가 진행 중이며 기록이 없을 때만 보류된 완주를 재시도한다. 기존 서버 중복 보호를 유지한다.
- 같은 경기에 복귀하면 서버가 마지막으로 받은 위치·방향을 적용하고 남은 로컬 이동/대시/공격 입력을 정리한다. 서버 기록상 완주한 경우 결과 대기로 복원한다. 새 플레이 씬으로 현재 경기에 진입할 때도 서버 위치부터 시작한다.
- 서버가 참가 만료를 확인하면 안내와 함께 방 목록으로 돌아간다. 이전 라운드가 바뀌었다면 현재 방 화면에서 안내하고 진행 중 경기 재개는 명시적으로 선택한다. 결과 상태라면 기존 결과 화면/같은 방 복귀 흐름을 따른다.
- 기존 UI·번역·서버 RPC를 재사용한다. 새 SQL/이미지/의존성/보상은 없다. 45초 서버 TTL을 넘긴 접속은 자동 재가입하지 않는다. 페이지 전체 새로고침 시에는 로그인 후 서버가 유지 중인 참가 정보만 복원할 수 있다.
- 전체 132개 테스트·타입 검사·프로덕션 빌드 통과. 추가 테스트: 응답 유실 Ready 읽기 복구, 완주 응답 유실 중복 방지, 실제 SQL TTL 만료와 목록 안내, 경기 조작 정지/위치 복구/만료 복귀, 백그라운드 늦은 응답 무시/리스너 정리. 실계정 2인 및 실제 모바일 네트워크 전환은 별도 확인 대상이다.

## 2026-10-20 멀티 캐릭터 구분·닉네임
- 본인 캐릭터는 기존 불투명도 1, 상대 캐릭터 컨테이너(착용·공격/대시 이펙트 포함)는 0.8로 표시한다. 블러/새 필터/이미지 변경은 없다.
- 닉네임은 서버 방 멤버의 name만 사용한다. 본인도 표시하며, 본인은 연두색·상대는 크림색이고 모두 짙은 외곽선을 갖는다.
- 이름은 동물 아트와 별도인 불투명도 1의 월드 레이어에 둔다. 발 위치에서 일정한 높이(155 월드 단위)에 배치하여 이동/점프/카메라를 따라가되 모션별 크기·좌우 반전의 영향을 받지 않는다. 상대 퇴장 시 이름도 함께 제거한다.
- 싱글 씬은 기존 모습과 동작을 유지한다. 기존 통합 테스트에 본인/상대 투명도, 닉네임 별도 레이어와 위치 검증을 추가했다. 실제 모바일 글자 크기·동물 겹침 시 가독성은 실기기 확인 대상이다.

## 2026-10-20 멀티 실기기 피드백 수정
- 위의 상대 alpha 0.8 방식은 사용자 피드백으로 폐기했다. 상대 컨테이너 alpha는 1, tint는 0xd9d9d9로 하여 몸/착용/효과를 약간 어둡게 표시한다. 본인과 닉네임 레이어는 원래 밝기를 유지한다.
- 레이스 RPC는 응답 후 추가 300ms 대기 대신 요청 시작 간격 목표 100ms로 갱신한다. 느린 응답에서는 완료 뒤 최소 16ms를 쉬고 다음 요청을 보내며 요청을 겹치거나 밀린 포즈를 쌓지 않는다. 대기방/목록 1.2초, 오류 2.5초 간격은 유지한다.
- 상대 위치 샘플이 변했을 때만 예측 기준 시각을 갱신한다. 제한한 RTT 절반과 원격 갱신 간격 절반을 수평 예측에 반영하며 최대 0.2초로 제한한다. 보간 지연을 줄이고 큰 위치 차이(리스폰 등)는 즉시 맞춘다. 끊김 상태에서는 추가 예측을 멈춘다.
- 여전히 소규모 RPC 방식이다. 두 기기의 전송/수신과 네트워크 왕복 지연이 존재하며 동시 사용자 증가 전에 실시간 전송 및 방 단위 동시성으로 확장해야 한다. 실제 네트워크 지연 수치는 자동 테스트로 주장하지 않는다.
- 방 안의 상시 맵 목록을 제거했다. 상단 현재 맵 옆 Choose map 버튼은 방장만 보이며 별도 팝업에서 기존 맵 카드를 2열·세로 스크롤로 선택한다. 배경 대기방은 inert, 팝업은 포커스 순환/Escape 닫기·이전 포커스 복귀를 지원한다.
- 맵 변경 성공 시 팝업을 닫는다. 서버의 방장 권한/대기 단계 제한/실제 맵 변경 시 Ready 초기화를 유지한다. 방장 변경·퇴장·경기 시작·언어 변경·상위 모달 종료 시 하위 팝업도 정리한다. 방 생성 시 맵 선택은 기존대로 유지한다.
- 전체 133개 테스트·타입 검사·빌드 통과. 기존 통합 테스트의 불투명 틴트/닉네임/이동 표시를 갱신하고 맵 팝업 선택→서버 변경→Ready 초기화→Escape/배경 복귀를 검증했다. 추가 SQL은 없다. 실기기 2인 반응 속도·패널 여백은 사용자 확인 대상이다.

## 2026-10-20 방 입장 차단 경로·맵 선택 위치 보완
- 사용자 증상: 다른 계정에서 방은 보이지만 클릭해도 입장하지 못함. 실제 사용자 세션의 오류 응답은 아직 직접 확보하지 못했으며, 코드에서 확인한 입장 차단 경로를 먼저 수정했다.
- 기존 create/join 전 클라우드 저장 완료를 기다리고 dirty가 남으면 save_pending으로 입장 RPC를 보내지 않는 처리를 제거했다. 꾸미기 저장은 백그라운드에서 시도하고, 저장 실패/지연과 무관하게 서버의 마지막 확정 모습으로 입장한다. 저장 실패 상태와 로컬 변경은 AccountService가 유지한다.
- RPC의 로그인 소유자 토큰 고정/방 정원/중도 입장 금지/RLS는 유지한다. 입장 실패 메시지는 이미 참가한 방/종료된 방/가득 차거나 진행 중인 방/인증·권한 오류를 구분한다.
- 대기방 상단의 '방장이 맵을 선택해요' 문구 위치를 Choose map 버튼으로 통일했다. 방장만 활성화하며 방원은 비활성 버튼으로 표시한다. 하단 인원 대기 안내 아래에는 맵 선택 목록을 넣지 않는다. 클릭 시 별도 팝업과 기존 서버 맵 변경/Ready 초기화를 사용한다.
- 테스트는 135개: 실제 SQL 두 계정 + 방 목록 카드 클릭 → 입장 → 방 유지 → Ready 공유, 꾸미기 저장 실패·미완료 중 입장 가능, 소유자 전환 시 RPC 차단을 추가했다. 실제 Google 계정 두 개 및 모바일 최종 확인은 별도로 필요하다. 추가 SQL은 없다.

## 2026-10-20 실시간 수신·순간 위치 보정 교체
- 방원에게 Choose map 버튼 자체를 표시하지 않는다. 방장에게만 상단 버튼/팝업을 제공한다.
- RPC 호출을 무작정 늘리는 대신 서버의 pose 변경을 방/라운드별 private Realtime 채널로 즉시 수신한다. 업로드 및 방·라운드·완주 검증은 기존 인증 RPC/100ms 목표 간격을 유지하며, 수신 측의 다음 RPC까지 기다리는 지연을 줄이는 구조다. 새 라이브러리는 없다.
- 새 `supabase/migrations/202610200004_room_stream.sql`은 구독 권한 검사 함수, realtime.messages 수신 정책/방 토픽 클라이언트 쓰기 금지 정책, 서버 pose 변경 트리거를 추가한다. 현재 라운드 참가자에게만 private 구독을 허용하고 클라이언트는 위치를 직접 Broadcast하지 않는다. 정책은 구독 시 평가되므로 퇴장/라운드 종료/로그아웃 시 클라이언트 구독도 해제한다. 구독 권한의 즉시 서버 강제 회수까지 구현한 구조는 아니다.
- 트리거는 pose가 실제 바뀌고 경기 진행 중일 때 id/pose/서버 시각만 보낸다. Realtime 발송 장애는 기존 pose RPC를 중단하지 않는다. 기존 방·참가자 테이블의 직접 접근 권한은 그대로 유지한다.
- RoomClient는 서버 시각 순서로 최신 pose만 수신한다. 수신한 위치를 오래된 RPC 응답으로 덮지 않으며 잘못된 멤버/좌표/이전 라운드의 늦은 이벤트를 무시한다. 구독 실패/SQL 미적용/실시간 샘플 만료 시 기존 RPC로 동작한다. 화면에 Live sync / Basic sync 상태를 표시한다.
- 이전의 '위치 차이 240 초과 시 즉시 이동'을 제거했다. RemoteMotion의 60ms 스냅샷 버퍼/최대 80ms 수평 예측/프레임당 연속 보정으로 교체했다. 서버 시간으로 패킷 간격을 보존하고 수평·수직 보정량을 제한한다. 초기 생성 위치 이외에 거리만으로 즉시 좌표를 바꾸지 않는다.
- 139개 테스트·타입 검사·프로덕션 빌드 통과. Supabase 소유 Realtime 함수만 로컬 mock으로 대체해 실제 migration/서버 트리거/RLS를 검증했다. 브로드캐스트 private/서버 ID, 비회원 구독 거부, 광범위 정책이 있어도 방 토픽 위조 쓰기 거부, 오래된 RPC/이벤트 무시, 구독 종료·소유자 확인, 지연된 대시 좌표의 연속 보정/예측 제한을 검증했다.
- 운영 SQL 적용은 사용자에게 요청했으며, 실제 Supabase WebSocket 및 두 기기 반응 속도 확인은 아직 남아 있다. 적용 후 페이지를 다시 열고 경기 화면에 '실시간 동기화'가 표시되는지 확인한다. 기존 RPC 업로드 지연·클라이언트 물리 한계는 남으므로 경쟁 게임 규모에서는 전용 시뮬레이션/전송을 추가 검토한다.
