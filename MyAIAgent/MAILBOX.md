# 우편함 (2026-10-24)

## 상태·알림·수령 합계 (2026-10-26, 이전 표시 규칙보다 우선)
- 목록은 미수령 → 수령 완료 → 기간 만료로 그룹화하고, 그룹 안에서는 최신 우편을 먼저 표시한다. 기존 목록/상세 패널과 Jua를 재사용한다.
- 실제 첨부가 없는 우편은 받기 대신 확인, 처리 후 확인 완료로 표시한다. 기존 claim RPC를 사용하므로 별도 보상이나 새 확인 테이블을 만들지 않는다.
- MailboxClient의 계정별 observer가 새 우편 도착 버전을 관리한다. 최초 조회·같은 응답 반복·오래된 목록 재노출에는 알림을 만들지 않는다. 로비 쪽지 버튼 아래에 새 우편 문구를 3.5초 표시한다. 기존 미수령 수 배지는 유지하며 알림 지연은 기존 30초 조회 주기를 따른다. 로비 재진입으로 과거 알림을 재생하지 않는다.
- claim/claim_all 응답의 received 합계는 서버 지급 트랜잭션에서 계산한다. 실제 지급한 코인·간식·새 의상 개수·가구/소품 수량과 확인한 공지 수를 표시한다. 이미 소유한 의상과 보관 한도로 차단된 우편은 보상 합계에서 제외한다. 부분 수령 성공 시 합계와 보관 한도 안내를 함께 표시한다.
- 합계는 현재 열린 패널에서 조회 갱신 후에도 유지하고, 닫았다 열거나 쿠폰을 등록하면 정리한다. 구버전 서버의 received가 없는 응답도 허용하며 일반 수령 안내로 대체한다. 브라우저는 표시만 담당하고 보상 값/지급 권한을 추가하지 않는다.
- SQL Editor 쿼리 이름: **Mail Receipt Summary**. 파일: `supabase/migrations/202610260019_mail_receipts.sql`. 기존 Player Mailbox and Rewards(013)가 선행되어야 한다. 우편/수령 기록·RLS·관리자 발송 권한을 유지한다. 사용자가 2026-10-26 SQL 추가 완료를 확인했다.
- 검증: 전체 304개 테스트·타입 검사·빌드 통과. 실제 PostgreSQL(PGlite)에서 부분 수령/중복 의상 제외/합계 검증/재실행/새 우편 알림 중복 억제를 확인했다. Chrome 960×600·640×440에서 패널 내부 버튼, 공지 확인, 수령 합계, 새 우편 알림을 검증했다. 화면 데이터는 모의 transport이며 실제 계정 보상은 발송하지 않았다.

## 쿠폰 입력 추가 (2026-10-25, 과거 미구현 설명보다 우선)
- 우편함 하단 `쿠폰 입력`으로 동일 패널 안에 코드 입력란·등록 버튼을 펼친다. 공통 Jua·설정 버튼을 재사용하며 Guest에게는 기존 로그인 안내를 표시한다. 입력란은 조회/요청 상태 갱신에도 같은 DOM을 유지하여 입력값·포커스를 보존한다. 한국어/영어, Escape/Tab 순환, 기존 모바일 입력 처리를 재사용한다.
- MailboxClient의 계정 고정 transport·observer·재시도를 재사용한다. redeem 요청만 `redeem_coupon(p_code)`로 보내며 브라우저는 코드만 전달한다. 실패 시 같은 코드를 재시도하고 로그아웃/계정 전환 이후 응답은 폐기한다.
- 서버는 코드 앞뒤 공백을 제거하고 대문자로 통일한다. 영문 대문자/숫자로 시작하는 4~40자, 이후 영문 대문자/숫자/하이픈을 허용한다. 쿠폰 시작·만료·활성 여부·총 사용 한도·계정별 1회를 검사하며 시도 간격은 계정별 2초다.
- `mail_coupons`, `mail_coupon_redemptions`, `mail_coupon_attempts`는 RLS와 권한 차단으로 일반 클라이언트가 읽거나 수정할 수 없다. 코드 등록은 SQL Editor 관리자만 한다. 전용 관리자 화면·임의의 기본 쿠폰·실계정 보상은 자동 생성하지 않는다.
- 쿠폰 행 잠금, 계정별 고유 사용 기록, `coupon:<쿠폰 UUID>` 발송 키를 같은 트랜잭션에서 처리한다. 기존 send_player_mail 검증/발송을 재사용한다. 재입력·응답 유실로 재시도해도 한 계정에 같은 보상 우편을 두 번 보내지 않는다. 등록 시 즉시 재화를 지급하지 않으며 기존 우편 수령을 거쳐 인벤토리에 반영한다. 발송 우편 기한은 등록 시점부터 30일이다.
- SQL Editor 쿼리 이름: **Mail Coupons and Rewards**. 파일: `supabase/migrations/202610250016_mail_coupons.sql`. 기존 **Player Mailbox and Rewards**(013)가 선행되어야 한다. 재실행 시 쿠폰/사용/우편 기록을 유지한다. SQL 실서버 적용 여부는 사용자 확인과 구분한다.

### 관리자 쿠폰 등록 예시 — 자동 실행하지 않음
SQL Editor에서 쿼리 이름 **Create Mail Coupon**으로 아래를 실행하면 테스트용 코드를 등록한다. `PAWHAVEN-TEST`를 게임 우편함에서 입력하면 코인 100개·간식 2개가 첨부된 우편이 도착한다. 필요에 맞게 코드·기한·보상을 수정한 뒤 실행한다. on conflict는 기존 쿠폰/사용 횟수를 초기화하지 않는다.

```sql
insert into public.mail_coupons(code,title,body,rewards,expires_at,max_uses)
values (
 'PAWHAVEN-TEST',
 '작은 선물이 도착했어요',
 '명랑이와 함께 따뜻한 하루 보내세요.',
 '{"coins":100,"snacks":2}'::jsonb,
 now()+interval '30 days',
 100
)
on conflict(code) do nothing;
```

- `max_uses=null`은 총 인원 제한 없음이며 계정당 한 번은 유지한다. enabled=false로 신규 사용을 중지한다. 이미 받은 우편은 유지된다. rewards는 아래 기존 발송 규격과 같으며 잘못된 보상은 등록 요청에서 서버 검증으로 거절되고 사용 횟수/우편이 반영되지 않는다.
- 로컬 실제 PostgreSQL(PGlite) 검증: 계정 격리·일반 계정 테이블 접근 차단·비로그인 거절·정규화·기간/활성/총량/시도 간격·잘못된 보상 원자적 실패·응답 유실 재시도·마이그레이션 재실행·우편 수령 후 재화/아이템 반영을 확인했다. Chrome 모의 transport 화면 검증은 실계정 지급과 별개다.
- 전체 269개 테스트·타입 검사·빌드 통과. Chrome 800px/640px 화면에서 쿠폰 입력 DOM/초안/포커스 유지, 등록 후 우편 표시·입력값 정리, 한국어 전환, 닫기 클릭 대상, 입력/하단 버튼의 패널 내부 배치를 확인했다.

## 컴포넌트와 서버
- MailboxClient는 계정에 고정된 transport·구독·30초 조회·실패 재시도를 담당하고 MailboxPopup과 LobbyHud가 이를 관찰한다. 계정 전환/종료 때 구독·타이머·진행 요청을 정리한다. 응답 유실 시 같은 우편 ID로 재시도한다.
- 서버 player_mail 테이블은 일반 클라이언트가 직접 읽거나 수정할 수 없다. mailbox_command RPC가 본인 우편만 반환한다. 목록은 유효 미수령을 우선해 최대 100개, 모두 받기는 한 번에 최대 100개다.
- public.send_player_mail은 service_role과 SQL Editor의 관리자만 호출할 수 있다. 일반 authenticated/anon에는 실행 권한이 없다. 브라우저는 보상 값이나 수신자를 지정하지 않는다. (user_id,delivery_key) 고유 키로 같은 발송을 재실행해도 중복 배달하지 않는다.
- 기존 economy_command(load)의 초기화·지갑 잠금 및 economy_items/economy_home_items/economy_wallets 저장 구조를 재사용한다. 서버에서 우편 만료·소유자·claimed_at·코인/간식/가구 한도를 검사한다. 한도가 찬 우편은 전체를 미수령으로 남기며 부분 지급하지 않는다. 모두 받기는 가능한 다른 우편만 수령한다.
- 수령과 지갑/아이템 반영은 같은 트랜잭션으로 완료한다. 응답을 잃고 재시도해도 claimed_at 때문에 두 번 지급되지 않는다. 수령 후 ServerShopState.reload로 기존 인벤토리·상점·간식 수량을 다시 읽는다.

## 관리자 발송 예시 (자동 실행하지 않음)
아래 USER_UUID를 Authentication → Users에 있는 수신자 UUID로 바꾼 후, SQL Editor에서 별도 쿼리 **Send Test Mail**로 실행할 수 있다. 이미 발송한 내용을 다시 보내려면 delivery_key를 의도적으로 바꿔야 한다. 서버 지급/쿠폰 검증 로직을 나중에 구현할 때도 같은 함수를 호출한다. service_role 키를 프런트엔드에 넣지 않는다.

```sql
select public.send_player_mail(
  'USER_UUID'::uuid,
  'mailbox-test-20261024',
  '작은 선물이 도착했어요',
  '명랑이와 함께 따뜻한 하루 보내세요.',
  '{"coins":100,"snacks":2,"items":[{"category":"Hat","index":2}],"home":[{"category":"Furniture","index":5,"quantity":1}]}'::jsonb
);
```

- coins: 0~100000, snacks: 0~99. items: 기존 Hat/Body/Acc/Etc 슬롯 1~20. home: Furniture 1~5, Etc 1~4, quantity 1~20. index/quantity는 JSON 숫자를 사용한다.
- 기본 기한은 30일이다. 6번째 인자 p_expires_at에 미래 시각을 지정할 수 있고 최대 366일이다. 지원하지 않는 보상 키나 중복 가구 키는 거절한다.
